title: Authentication
description: Import an authorized browser session, with optional Galleton-managed renewal.

Wallapop has no password API worth using. Google, Apple, Facebook and password accounts all end
up at the same place, a session cookie in your browser. The CLI imports that cookie and then
renews it locally or delegates renewal and encrypted storage to Galleton.

<Callout type="idea" title="Why a cookie">
  An email and password login was tried and rejected; see ADR 0001 in the repository. Cookie
  import is the single supported path because it works identically for every account type.
</Callout>

## Export the cookie

<Steps>
<Step>
### Install a cookie exporter

Any extension that exports Netscape-format cookies works. Cookie-Editor and "Get cookies.txt"
are the common ones.

![Cookie-Editor homepage, showing the supported browsers and the import/export feature](/auth/cookie-editor-home.png)
</Step>

<Step>
### Log in to Wallapop in your browser

Go to `es.wallapop.com` and sign in.
</Step>

<Step>
### Export cookies for the site

Export for `wallapop.com` and save the file. You need `__Secure-next-auth.session-token`; the
CLI also picks up `device_id` if it is there.

![Cookie-Editor feature list with the import and export option](/auth/cookie-editor-export.png)

<Callout type="warn" title="Cookie-Editor exports JSON by default">
  The CLI reads Netscape format, pasted `name=value` pairs, or a bare cookie value. If your
  exporter offers a format choice, pick Netscape or "cookies.txt".
</Callout>
</Step>

<Step>
### Import it

```bash
wallapop auth login --cookies ~/Downloads/cookies.txt
```

Or run the interactive prompt and paste the cookie value when asked:

```bash
wallapop auth login
```

`--cookies-stdin` reads until end-of-file; use it when piping an export into the command.
</Step>
</Steps>

Login validates the session and tells you who you are, so a bad export fails at once
rather than three commands later. It also saves your account's location as the default search
location. Your first search already works.

## Galleton-managed sessions

To replace the CLI's in-process renewal with [Galleton](https://github.com/Microck/galleton),
start its daemon with the repository's `examples/galleton.wallapop.json` adapter and set
`WALLAPOP_GALLETON_DIR` to the daemon's private state directory. Then use the same login
command, or run `wallapop auth status --check` to migrate an existing profile.

After a successful migration, `credentials.toml` holds a `galleton_id` and account metadata,
not the cookie. The daemon owns renewal and rotated credentials. Managed profiles never
fall back to local renewal when the daemon is down. Unconfigured, unmigrated profiles keep
the existing behavior; `WALLAPOP_SESSION_TOKEN` remains a non-persistent local override.

See the [setup and migration guide](https://github.com/Microck/wallapop-cli/blob/main/docs/galleton.md)
for connection settings, watch/MCP service configuration, recovery, and security limits.

## Staying logged in

Wallapop can rotate the session cookie as it is renewed. Galleton persists rotations for
managed profiles; the CLI does so for legacy profiles. Renewal cannot override provider
expiry, revocation, or a requirement to log in again.

```bash
wallapop auth status          # local metadata; works offline
wallapop auth status --check  # verify that a usable API token is available
wallapop auth refresh         # request renewal; nonzero exit on failure
```

Managed status reports `source: "galleton"` and the daemon session ID. Cookie expiry is
omitted because the daemon does not expose it; use `galleton status` for renewal details.

## Profiles

Each account gets its own session, location and watches.

```bash
wallapop auth login --cookies alt.txt --profile alt
wallapop profile list
wallapop profile use alt      # change the default
wallapop search "bici" --profile alt
```

## In CI

Pass the cookie by environment variable and no credentials file is needed:

```bash
export WALLAPOP_SESSION_TOKEN="..."
wallapop search "bici" --format jsonl
```

## Where things live

<Files>
  <Folder name="$XDG_CONFIG_HOME/wallapop-cli" defaultOpen>
    <File name="config.toml" />

  </Folder>
  <Folder name="$XDG_DATA_HOME/wallapop-cli">
    <File name="state.db" />
  </Folder>
</Files>

The CLI keeps `credentials.toml` separate from `config.toml` and writes it at mode `0600`, so sharing
your config never leaks your session.

## Log out

```bash
wallapop auth logout --profile alt   # keeps config and watches
wallapop profile remove alt          # removes everything for that account
```

For managed profiles, these commands forget the daemon session first. A daemon outage
fails the command without discarding the local reference, so removal can be retried.
